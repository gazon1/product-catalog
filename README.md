# product-catalog

Витрина товаров: читает базу краулера **только на чтение** и показывает каталог, цены, кэшбэк и историю цен.

Ни ASP.NET, ни ORM, ни миграций: Next.js обращается к PostgreSQL напрямую.

---

## Что это за проект и чего в нём нет

Проект **не владеет схемой**. Он читает `crawl_targets` и `scraped_items` из базы краулера и не изменяет их. Поэтому здесь нет:

| Нет | Почему |
|---|---|
| ORM | Каждая из шести страниц читает предсказуемый набор колонок; ORM добавил бы слой, который пришлось бы обходить при каждом новом запросе |
| Миграций | Схемой владеет краулер. `just schema-sync` **копирует** его миграции в `dev/db/` для локальной БД, гейт падает, если копия разошлась, а `tests/database.test.ts` прогоняет настоящие запросы витрины против получившейся схемы |
| API-слоя | Предыдущее решение держало ASP.NET Core между Next.js и базой — 1599 строк C#, которые переводили названия колонок в другие названия. Здесь SQL — единственное место, где встречаются имена колонок |
| Кэша страниц на сборке | Сборка не открывает подключение к базе (см. «Известные ограничения») |

## Почему read-only гарантируется трижды

База принадлежит другому репозиторию, у которого нет возможности обеспечить дисциплину с нашей стороны. Поэтому граница защищена на трёх уровнях, и убрать любой один — значит остаться с двумя:

1. **Роль в Postgres — `SELECT`-only.** Это контракт; настраивается один раз при выдаче доступа. Скрипт выдачи — [`deploy/provision-readonly-role.sql`](deploy/provision-readonly-role.sql), и запускает его тот, кто администрирует базу краулера, **не** деплой витрины: раздавать себе права на чужую базу — ровно та привилегия, которую эта схема и сдерживает. Скрипт идемпотентен и выдаёт только `CONNECT`, `USAGE`, `SELECT`.
2. **Сессия:** каждое соединение из пула открывается с `default_transaction_read_only=on`. Ошибка в строке запроса может дать неверный результат — но не запись. Плюс `statement_timeout` и `timezone=UTC`.
3. **Код:** гейт `tests/architecture.test.ts` падает, если в `src/lib/**` появится `INSERT`/`UPDATE`/`DELETE`/`CREATE`/`ALTER`/`TRUNCATE`/`GRANT`.

Уровень 1 — единственный, который живёт вне репозитория, поэтому проверяется он тем, что доступно здесь: `tests/read-only-role.test.ts` падает, если скрипт выдачи начнёт раздавать что-то помимо чтения, отменит или удалит гранты краулера, возьмёт пароль литералом или потеряет запрос проверки. Проверено контролем: подставленный `GRANT ALL PRIVILEGES` роняет гейт с указанием строки.

**Что должен сделать краулер, а не оператор.** `ALTER DEFAULT PRIVILEGES` действует только на объекты, создаваемые той ролью, которая его выполняет. Выполненный администратором, он не покроет ни одной таблицы — их создаёт краулер. Поэтому каждая его миграция обязана добавлять:

```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO catalog_readonly;
```

Без этого скрипт выдачи отработает успешно, а витрина не прочитает таблицу из следующей миграции. Скрипт выдачи это фиксирует в комментарии и гейтом, и README.

Проверка после выдачи — в самом скрипте. Утверждать нужно отсутствие прав на запись, а не наличие гранта: роль в списке доказывает, что что-то выдали, и только отсутствие write-привилегий доказывает, что граница цела.

## Быстрый старт

```bash
just db-up     # PostgreSQL 16 + миграции краулера + синтетические данные
just dev       # http://localhost:3000
```

`just db-reset` пересоздаёт базу с нуля — entrypoint Postgres применяет `dev/db/*` только при первом создании тома, поэтому изменение миграции без сброса ничего не даёт.

### Данные в dev — синтетические

Краулер ещё не ходил по настоящему API, поэтому `just schema-sync` генерирует `dev/db/99-seed.sql`: 8 каталогов, ~2900 наблюдений товаров, детерминированный PRNG.

Генератор намеренно воспроизводит состояния, которых нет в «идеальных» данных, потому что именно они ломают вёрстку:

- каталог настроен, но пуст (`Зимняя резина`);
- 15 % карточек без картинки — срабатывает заглушка;
- у части товаров нет цены, скидки, кэшбэка или `match_id`;
- один товар встречается в нескольких каталогах — срабатывает `DISTINCT ON (match_id)` в «Топе по кэшбэку»;
- у товара несколько наблюдений цены — строится график истории.

Перегенерировать: `npm run seed`. Побочный эффект — ноль: генератор детерминирован, повторный запуск даёт байт-в-байт тот же файл.

## Проверка

```bash
just check     # typecheck → schema-check → tests → test-runs → build
```

145 тест: денежная арифметика, слаги, склонение, разбор query-параметров, качество сгенерированных данных, **архитектурные инварианты** и **контракт с краулером против настоящего Postgres**.

| Гейт | Что не даёт |
|---|---|
| `architecture.test.ts` | `INSERT`/`UPDATE`/`CREATE` в `src/lib/**`; потерю read-only-guard; незакрытый whitelist сортировки; `ORDER BY` без tiebreaker. Комментарии вырезаются перед сканом — иначе гейт ловил бы английское слово «copy» в JSDoc, и единственным «фиксом» было бы переписать комментарий |
| `query-building.test.ts` | Коллизию плейсхолдеров `$n` между фильтром и `LIMIT` — ошибку, которая даёт 42804 только на страницах с `target_id` |
| `server-rendering.test.ts` | `loading.tsx` в корне (HTML становится скелетом); обработчики событий в Server Component |
| `seed-data.test.ts` | Кэшбэк в рублях больше цены — ту же ошибку единиц, что краулер уже развёл по двум колонкам |
| `read-only-role.test.ts` | Скрипт выдачи роли, который начнёт раздавать права помимо чтения, отменит гранты краулера или возьмёт пароль литералом |
| `database.test.ts` | Миграцию краулера, после которой запросы витрины перестают работать: поднимает `postgres:16-alpine`, применяет настоящие `dev/db/*.sql` и сид (8 целей, 2902 наблюдения), затем зовёт **production-функции** `listItems` / `getProduct` / `listTopDeals` / `listTargets` / `getSiteStats` |

Каждый из этих гейтов написан по реально найденной ошибке, а не по гипотетической — подробности в комментариях к тестам. `database.test.ts` нашёл три живых бага в `src/lib/queries.ts` (`listTopDeals` фильтровал по несуществующему алиасу `s`, `DISTINCT ON` ломал сортировку по кэшбэку, не-UUID в URL давал ошибку БД вместо 404), и проверку дрейфа схемы он проходит: правдоподобная V3, переименовывающая `match_id`, роняет 4 теста с указанием колонки.

### «Тесты зелёные» ≠ «тесты выполнились»

`npm test` завершается с кодом 0 и печатает сводку независимо от того, выполнилось 145 тестов или один файл выпал из `include`. Отсутствие Docker уже ловится отдельно и громко (`global-setup.ts` бросает исключение), но остаётся дыра похуже: набор, который **никогда не был выбран**, до гейта, способного пожаловаться, не доходит.

`scripts/check-test-runs.py` читает JUnit XML, который пишет прогон, и сверяет его с `config/test-runs-floor.tsv`. Пол задан **на каждый файл**, а не на сумму: сумма в 145 позволила бы росту остальных файлов замаскировать исчезновение `database.test.ts` — того единственного, который разговаривает с базой.

Проверено контролем: `npx vitest run tests/slug.test.ts` отчитывается `1 passed` и выходит с 0, гейт выходит с 1 и называет каждый невыполненный файл.

**Осознанное расхождение с краулером.** У него `check-test-runs.py` задаёт пол на модуль Gradle и явно документирует слепое пятно. Здесь оно закрыто пофайлово: под угрозой там «добавили тест, а задача перестала его выбирать», здесь — «единственный набор, работающий с базой, перестал запускаться», а такое здесь уже приходилось ловить. Расхождение зафиксировано здесь и в шапке скрипта, а не оставлено на волю случая.

### Нужен Docker

`npm test` поднимает контейнер, поэтому без работающего Docker-daemon набор **падает, а не пропускается**. Зелёный прогон, в котором 30 тестов к Postgres не выполнились, хуже отсутствия тестов — это ровно тот дефект, который остальные гейты репозитория и ловят.

Миграции для тестов находятся по каталогу `dev/db/`, а не перечислены списком: как только у краулера появится V3 и `just schema-sync` её скопирует, набор подхватит её сам. Список в коде был первой версией и был неверен — гейт синка стал бы зелёным, dev-БД применила бы V3, а тесты продолжали бы проверять старую схему.

**Известное косметическое предупреждение:** каждый прогон заканчивается `close timed out after 10000ms … something prevents Vite server from exiting`. Код возврата 0, все тесты выполнены и отчитались; открыт поток логов контейнера testcontainers, а не соединение с БД (его `database.test.ts` закрывает явно). Поднимать `teardownTimeout` пробовали — становится хуже. Зафиксировано в шапке `tests/global-setup.ts`.

## Развёртывание

Готово по формату `dacha-na-udachu-website`: образ в GHCR, `workflow_dispatch` для выката, гейт дрейфа Caddy-маршрута через `sha256sum`, smoke-test через публичный домен.

```bash
just route product-catalog deploy/caddy.conf.caddy   # из репозитория Caddy-vps
```

**Перед первым выкатом заменить** в `deploy/caddy.conf.caddy` домен `shop.maxdrobin.ru` на настоящий — сейчас это плейсхолдер, и файл ни разу не сравнивался с работающим сервером. Задать в репозитории переменные `CRAWLER_REPO` и `PUBLIC_URL`.

Отличия от предыдущего решения: в `deploy.yml` **нет шага миграции** — витрина не может изменить базу, поэтому выкат нечего откатывать; `docker compose` на сервере не содержит сервиса `db`.

## Известные ограничения

Честный список, а не «работает идеально»:

1. **Отсутствующий товар или категория отвечают статусом 200, а не 404.** Контент 404-страницы корректный, статус — нет: в Next 15.4.11 `notFound()` в динамическом сегменте не может изменить статус после начала стриминга. Проверено и с `force-dynamic`, и без — причина не в режиме рендера. Смягчено тремя способами, все работают: `noindex` в метаданных для несуществующих страниц, `canonical` только для существующих, в `sitemap.xml` только непустые категории.

2. **Нет ISR на статических по пути маршрутах.** `/` и `/catalog` помечены `force-dynamic`, поэтому пересчитываются на каждый запрос. Причина — реальный баг: первый `next build` пререндерил их при отсутствующем `DATABASE_URL`, запросы упали, страницы были запечены как «данных нет», а сборка завершилась `BUILD SUCCESSFUL`. Данные динамических сегментов (`/category/[slug]`, `/product/[id]`) кэшируются на 60 с через ISR по требованию — там нет `generateStaticParams`, поэтому сборка базу не трогает.

3. **`listTargets()` — полный проход по `scraped_items`.** Единственный запрос, который не масштабируется бесплатно; кэшируется на 10 минут. Правильное решение — поддерживаемый счётчик, а это запись в чужую базу.

4. **Слаги производные.** Схемы нет — значит, нет и колонки `slug`. Slug транслитерируется в JS и сопоставляется в памяти по списку целей; при совпадении у двух целей страница отдаёт 404, а не угадывает. Переименование каталога меняет его URL.

5. **Сортировка требует одного клика.** Форма сортировки — обычная GET-форма, без `onChange`: обработчик события нельзя передать в Server Component, а Next падает на этом при рендере. Авто-отправка стоила бы клиентского компонента и зависимости от JS.

6. **Цена и кэшбэк — на момент последнего обхода.** Дата показана явно, но это снимок, а не котировка.

```

tests/         vitest, включая архитектурные гейты
```
